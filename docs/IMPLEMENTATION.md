# 구현 결과와 운영 전 남은 작업

2026-10-25 · 원본 소스를 확장했으며, 현재는 Git 저장소 루트에 `package.json`, `src/`, `server/`를 바로 두는 구조다. 원본 자료는 별도 작업 폴더에 보존하고 실행·공유에 필요한 소스와 문서를 이 저장소에 모았다.

## 구현한 범위

- 원본 `지침/openapi.yaml`의 80개 작업을 Express API에 연결했다. 요청 본문·쿼리·헤더와 JSON 응답은 복사된 `docs/openapi.yaml`로 검증한다. 프론트 타입도 여기서 생성한다.
- SQLite에 사용자, 해시 처리한 인증 토큰, 매장, 메뉴, 파티, 참가자, 후보 집합, 열람/소거, 생성 작업, 초대, QR, 주문, 수수료, 감사·분석 이벤트를 저장한다. 소규모 단일 서버용으로 리소스별 JSON 행을 사용한다. 주문과 수수료의 유일성은 DB 인덱스로 보장한다.
- 모든 API 명령은 즉시 트랜잭션에서 권한·상태·버전·멱등성을 검사하고 결과와 outbox를 함께 저장한다. SSE 전송은 커밋 후 별도로 수행한다. 제출 가격 충돌은 최신 초안과 완료 해제를 저장한 다음 409로 반환한다.
- 사용자·초대 게스트·QR 주문 게스트·방장·사업자 범위를 구분한다. 다른 참가자의 제한 상세와 소거자, 소거 인원수는 공용 응답 및 이벤트에 포함하지 않는다.
- 로그인·회전·로그아웃, 파티 초대/참가/탈퇴/강퇴/이름 수정, 개인 제한 수정·확인, 비동기 음식/식당 후보 생성, 공동 소거·본인 복구, 전원 완료·방장 확정, 최종 식당 선택을 연결했다.
- 매장/메뉴/재료·제한/가격/옵션/품절/숨김 관리, QR 발급·다운로드·폐기, 파티 연결, 일반 QR 주문, 개인 항목 추가/수정/삭제, 공동 주문 제출, 전체 수락/거절, 수수료 조회를 연결했다.
- SSE 3종은 Bearer fetch 스트림, 본인 전용 열람 이벤트, 24시간 재전송, 커서 만료, 재연결 후 최신 상태 재조회, 연결 종료 시 권한 재검사를 지원한다. 접속 상태는 스트림 연결로 표시하며 오프라인 참가자를 자동 완료하지 않는다.
- 게스트는 종료 또는 24시간 후 만료한다. 게스트 제한은 개인 저장소·파티 전용 제한 스냅샷·인증 주체별 응답 캐시에서 삭제한다. 주문 스냅샷에는 제한을 복사하지 않는다.
- 지도 반경은 200~1000m, 10m 단위다. 새 소비자용 `GET /restaurants/nearby-count`는 DB 등록 식당 수를 계산한다. 원본 계약의 파티 반경 100~5000m는 유지했다.
- 시연 모드에서만 가상 매장과 닉네임/사장님 로그인을 제공한다. 운영 모드는 시연 계정 발급 경로를 설치하지 않는다. 개발 샘플 `/dev/sample-party/menu`도 유지한다.

## 화면 피드백과 누락 동작 보완

- 홈의 파티 만들기 문구를 버튼 중앙에 맞추고 더하기 아이콘을 SVG로 표시한다.
- 장소 검색과 함께 지도 클릭·핀 드래그로 좌표를 지정하고 주소를 역변환한다. 상세 만날 위치는 기존 `location.address`에 줄바꿈으로 저장해 API 계약과 기존 주소를 유지한다. 수정·재접속 후에도 좌표와 상세 위치가 남는다. 선택 약속 시간과 예산 제한 없음도 생성·수정 화면에 연결했다.
- 음식·식당 카드를 55% 이상 250ms 보거나 확인 버튼을 누르면 열람 기록을 저장한다. 성공한 저장만 개수에 반영하고 최신 서버 진행률까지 일치해야 검토 완료를 허용한다. 저장·진행률 조회 실패는 화면에서 재시도할 수 있다. 소거된 후보도 확인하며 서버는 중복·과거 후보 ID를 확인 개수에서 제외한다.
- 식당에도 드래그·소거 모션을 적용한다. 짧은 드래그와 세로 스크롤은 소거하지 않으며 저장 실패 시 카드가 돌아온다. 기존 복구·되돌리기와 모션 줄이기 설정을 유지한다. 후보 변경으로 검토 완료가 해제되면 이유와 참가자 완료 현황을 표시한다.
- QR 화면은 해당 매장으로 확정된 방장 파티만 표시하고 복수 선택을 지원한다. 파티 조회 중이거나 실패해도 일반 QR 주문은 사용할 수 있다.
- 주문 항목의 옵션·요청사항을 수정하고 저장 실패 시 입력을 유지한다. 주문 제출 전 방장은 주문 화면에서도 최신 상태·버전을 확인한 뒤 파티를 취소할 수 있다. 음식 검토 화면에도 파티 관리 진입점을 제공한다.
- 최초 서버 연결 실패에는 재시도 버튼을 제공한다. 반경 200~1000m와 등록 식당·메뉴 기준은 유지한다.
- 이미 로그인한 사용자도 초대 화면에서 입력한 이름을 파티 표시명으로 저장한다. 파티 참가자 목록·헤더·검토 프로필·주문 화면은 해당 파티의 표시명을 사용하며 새로고침 뒤에도 유지한다.
- 사용자는 QR 링크를 직접 입력하는 대신 후면 카메라로 매장 QR을 스캔한다. iPhone·Android 공통 이미지 디코더를 사용하고 카메라 불가 시 QR 사진 인식을 제공한다. 홈에서는 매장 진입, 식당을 정한 파티에서는 방장의 매장 연결로 이어진다. 닫기·인식 완료·화면 종료 때 영상 트랙을 정리하며 서버의 선택 식당·QR 유효성 검증은 유지한다.

## 로그인과 데이터

릴리스 브랜치는 실행 중인 `data/demo.sqlite`를 Git에서 제외한다. 로컬 파일은 유지하며 공유하지 않는다. 새 설치의 기본 시연 모드는 최초 실행 시 공개 카탈로그 식당 7곳·메뉴 90개와 통계 자료를 생성한다. 이미 초기화된 DB에는 재시작 시 덮어쓰지 않는다. 테스트가 명시한 별도 카탈로그와 일반 운영 모드는 통계 자료를 자동 생성하지 않는다. 따라서 팀원이 새로 받아도 같은 시연을 할 수 있지만 개인 세션·주문 이력은 전달되지 않는다.

`release/1.0.0` 검증: 새 DB 초기화·기존 수정 내용 보존 검사를 포함한 API 테스트 22개, 브라우저 전체 시나리오 23개, TypeScript·배포 빌드가 통과했다. 카테고리 대안은 생존 모임 수 기준 상위 5개를 표시한다.

소비자는 게스트 시작·닉네임/로컬 로그인·초대 게스트·QR 주문 진입 시 기본 정보가 없으면 만 나이(1~120세)와 성별을 저장해야 다음 화면으로 이동한다. 기존 사용자는 첫 재접속 때 입력하고 이후에는 다시 묻지 않는다. 홈의 `내 기본 정보 수정`에서 수정한다. 성별은 여성·남성·기타·응답 안 함 중 선택한다. 사장님 관리 진입은 소비자 입력을 요구하지 않는다.

사장님 매장 관리의 `통계`에서 최근 3일·일주일·한 달을 선택한다. 한국 시간 오늘 포함 접수일 기준으로 접수/대기/수락/거절/제출 후 취소, 수락 주문 금액과 평균, 일별 추이, 인기 메뉴 상위 10개를 표시한다. 인기 메뉴는 수락 주문의 수량순이며 옵션 금액을 포함한다. 고객 구성은 수락 주문 참여 인원의 연령대·성별 합계로 재주문을 각각 센다. 주문 제출 당시 익명 합계를 고정해 나중의 프로필 수정/게스트 정보 삭제에도 통계가 유지된다. 기존 정보 없는 주문은 미입력으로 표시한다. 매장 소유권을 서버에서 검사하며 타인 프로필/개별 연령은 사업자에게 제공하지 않는다. 추가 계약은 `docs/api-extensions.yaml`에 기록했다.

`전체 가게 인기 카테고리`는 우리 가게와 다른 가게의 수락 주문을 카테고리별 수량으로 합산하고, 가게명과 다른 가게 식별자를 표시하지 않는다. 주문 제출 당시 카테고리를 별도 집계로 저장해 이후 메뉴 수정에도 유지한다. 이전 주문은 저장된 메뉴의 현재 카테고리로 분류한다. `우리 음식 대신 살아남은 카테고리`는 기간 내 음식 검토 확정된 전체 모임 중 우리 매장 메뉴 카테고리가 하나 이상 소거된 모임을 분석한다. 그 모임들에서 살아남은 다른 카테고리를 모임 수와 비율로 보여주며, 진행 중 검토·소거 후 복구·전혀 소거되지 않은 우리 카테고리는 조건에 포함하지 않는다. 복수 생존은 중복 집계하므로 비율 합계가 100%를 넘을 수 있다. 원본 파티/후보 공개 계약을 유지하며 확정 결과만 별도 익명 합계로 저장한다.

`npm run stats:seed -- --apply`는 기존 `data/demo.sqlite`를 온라인 백업한 뒤 최근 30일 통계 자료를 채운다. 주문·파티·사용자·메뉴·수수료 실데이터를 수정하지 않고 별도 분석 자료만 저장해 접수 목록에는 섞이지 않는다. 반복 실행 시 해당 분석 자료만 교체한다. 화면에는 별도 배지를 표시하지 않으며 일반 실행(시연 모드가 아닌 운영 API)은 이 자료를 집계하지 않는다. `--apply` 없이 실행하면 트랜잭션을 되돌려 예상 개수만 확인한다.

2026-10-25 적용: 등록 매장 7곳에 최근 30일 주문 1,144건·음식 검토 535건을 반영했다. 백업과 대조해 기존 리소스 439건의 내용이 그대로인 것을 확인했고, 7개 매장 모두 3/7/30일 통계·고객 구성·생존 대안이 표시되는지 확인했다. 기본 정보 검증/수정/게스트 정리, 타 매장 접근 차단, 카테고리 합산/과거 고정, 기간 경계, 익명성, 자료 재실행과 운영 모드 제외를 포함한 서버 테스트 21개가 통과했다. 기본 정보·실제 공동 주문·채워진 카테고리 통계 브라우저 시나리오 7개를 추가 실행해 통과했고 기존 화면 회귀도 확인했다. TypeScript·배포 빌드와 Git 공백 검사도 통과했다.

`npm run dev`는 명시적인 시연 모드다. 새 브라우저마다 새 시연 사용자로 시작하며 사장님 버튼은 공통 시연 사업자 계정으로 들어간다. 시연 자료는 `data/demo.sqlite`에 저장된다. 실제 SNS 로그인으로 표시하지 않는다.

운영용 선택지는 `LOCAL_AUTH_ENABLED=true`로 켜는 서버 발급 계정 로그인이다. `npm run create:user`로 사용자/사업자 계정을 만들고, 이메일·비밀번호 검증 → 60초 단일 사용 코드 → 명세의 `/auth/login` 교환을 사용한다. 비밀번호는 scrypt와 무작위 salt로 저장하며 사업자 역할을 클라이언트에서 지정할 수 없다. 기본 운영 DB는 `data/xiro.sqlite`이며 가상 식당·사용자를 자동 등록하지 않는다. 기준 카테고리와 재료 코드는 제공한다.

SNS/OIDC 공급자 검증·콜백·계정 연결과 공개 회원가입·계정 복구는 아직 구현하지 않았다. 로컬 인증은 운영자 발급 계정을 위한 구현이다. 운영 인증 정책에 맞춰 이 부분을 결정해야 한다.

실제 휴대전화 두 대·운영 HTTPS 환경·실제 카카오 SDK 검색의 현장 검증은 아직 하지 않았다. 외부 지도 테스트는 기존 어댑터 모의 검증과 구분한다.

## 아직 필요한 운영 결정과 작업

1. 운영 도메인·호스팅·TLS 인증서·프록시·영구 DB 볼륨·백업 주기와 복구 책임자 지정. 배포는 수행하지 않았다.
2. 실제 SNS 공급자 또는 로컬 발급 계정 운영 정책, 회원가입/복구, 매장 소유권 확인과 사업자 심사 절차 결정. 이 구현은 소유권 심사를 자동화하지 않는다.
3. 임시 정책 승인: 정원, 기준 코드 목록, 게스트/감사/분석 데이터 및 백업 보관·삭제 정책, 요청률 제한, SSE 보관 기간. 현재 기본 정원 8명, 이벤트/멱등성 보관 24시간이다.
4. 수수료 요율·반올림·과세 정책 결정. 모든 수락 주문은 정책 미정의 `PENDING`, 금액·요율 `null`로 기록한다. 임의의 비율, 청구/출금, 결제 기능은 추가하지 않았다.
5. 부하·장애·복구 검증과 로그 수집/모니터링. 현재는 단일 Node 프로세스와 SQLite용이다. 다중 API 프로세스/다중 인스턴스 배포 전 DB·작업·접속 상태·rate limit을 공유 저장소로 이전해야 한다.
6. 관리자/광고/고급 분석/AI 자유 분류는 이 API 명세의 범위 밖이다. 후보는 등록된 카테고리와 구조화된 재료 코드로 판정하며 외부 AI를 호출하지 않는다.
