# 시로 개발 예상 질문과 모범 답안

답변은 현재 구현을 기준으로 했다. 굵게 표시된 첫 문장을 중심으로 말하고, 추가 질문이 나오면 뒤의 설명을 이어 말하면 된다.

## 1. 직접 개발한 핵심 기능은 무엇인가요?

**여러 사람이 같은 화면을 보면서 싫은 음식을 제외하고, 남은 음식에 맞는 식당을 골라 함께 주문하는 흐름입니다.** 카카오맵으로 장소를 정하고, 각자의 식사 제한과 예산을 반영해 후보를 만듭니다. 이후 공동 소거, QR 매장 연결, 개인별 메뉴 선택, 사장님의 주문 수락까지 서버와 DB로 연결했습니다.

## 2. 카카오맵이 해주는 일과 직접 만든 부분은 어떻게 다른가요?

**카카오맵은 지도와 장소 검색을 담당하고, 모임과 식당 선택 규칙은 저희가 구현했습니다.** 지도 위 약속 장소는 카카오맵 SDK로 정하지만, 주변에 있는 등록 식당을 찾고 거리·예산·식사 제한으로 후보를 거르는 것은 저희 서버와 DB가 처리합니다. 카카오맵에 있는 모든 식당에서 주문이 가능한 구조는 아닙니다.

## 3. 음식 추천에 AI를 사용했나요?

**현재는 AI가 아니라 명확한 조건으로 후보를 거르는 방식입니다.** 등록 메뉴의 가격·재료·음식 카테고리와 참가자의 조건을 비교합니다. 그 안에서 참가자들이 싫은 음식을 제외하도록 해서 선택 과정을 만들었습니다. 현재 구현을 AI 추천이라고 설명하지 않습니다.

## 4. 알레르기나 식사 제한은 어떻게 반영하나요?

**참가자들이 등록한 제한을 모아서 메뉴의 재료 정보와 비교합니다.** 맞지 않는 메뉴나 필요한 재료 정보가 부족한 메뉴가 있는 카테고리는 후보에서 제외하는 보수적인 기준을 적용했습니다. 등록 정보만으로 판단하므로 실제 조리 환경까지 확인하거나 알레르기 안전을 보장하는 기능은 아닙니다.

## 5. 한 사람이 음식을 제외하면 다른 사람에게 어떻게 보이나요?

**서버가 SSE라는 방식으로 바뀐 내용을 다른 참가자에게 알려줍니다.** 사용자의 동작은 일반 API 요청으로 받고, 다른 사람의 화면에 알려주는 것은 서버가 담당합니다. 각자 새로고침하지 않아도 공동 소거와 검토 완료, 주문 상태를 확인할 수 있습니다.

## 6. 왜 WebSocket 대신 SSE를 선택했나요?

**이 서비스는 서버가 참가자에게 변경 사항을 알려주는 일이 중심이라 SSE가 잘 맞았습니다.** 사용자 입력은 이미 API로 보낼 수 있어서 양방향 통신을 별도로 계속 유지할 필요가 적었습니다. 연결이 끊어지면 재접속하고 놓친 이벤트나 최신 상태를 다시 확인하도록 했습니다.

## 7. 두 사람이 동시에 같은 음식을 제외하면 오류가 나지 않나요?

**소거 결과를 각자의 휴대전화가 아니라 서버에서 관리합니다.** 한 명이라도 제외한 음식은 소거 상태로 남습니다. 본인이 한 소거만 취소할 수 있고, 누가 제외했는지는 다른 참가자에게 보여주지 않습니다. 중요한 확정 작업은 최신 버전인지도 검사합니다.

## 8. 주문 버튼을 두 번 누르면 주문도 두 개 생기나요?

**중복 전송에 대비해 요청에 고유 번호를 붙이고, 같은 요청은 한 번 처리한 결과를 돌려줍니다.** 이 번호가 `Idempotency-Key`입니다. 주문 상태와 버전도 검사해서 제출이 끝난 주문을 다시 제출하거나 두 번 수락하는 것을 막습니다.

## 9. 메뉴를 고르는 중에 가격이 바뀌거나 품절되면 어떻게 하나요?

**메뉴를 고를 때뿐 아니라 선택 완료와 주문 제출 때도 최신 정보를 다시 확인합니다.** 가격이 달라졌다면 새 가격을 보여주고 선택 완료를 다시 받습니다. 판매할 수 없는 메뉴나 옵션은 그대로 주문을 넘기지 않고 오류를 알려줍니다.

## 10. QR코드는 어떤 역할인가요?

**현재 고른 매장과 주문을 연결하는 입구입니다.** 카메라로 QR을 읽으면 어느 매장인지 서버에서 확인하고 그 매장의 메뉴를 고를 수 있습니다. 파티가 정한 매장과 다른 매장의 QR은 연결하지 못하게 했습니다. 카메라를 사용할 수 없을 때는 QR 사진을 선택해 인식할 수도 있습니다.

## 11. 사장님이 다른 가게의 주문이나 고객 정보를 볼 수 있나요?

**주문 관리와 개별 매장 통계는 본인 매장만 조회하도록 서버에서 검사합니다.** 전체 가게의 인기 음식은 가게 이름 없이 카테고리별 합계로만 보여줍니다. 고객 구성도 개별 이름이나 정확한 나이 대신 연령대와 성별별 인원수로 표시합니다.

## 12. ‘우리 음식 대신 살아남은 카테고리’는 어떻게 계산하나요?

**우리 가게가 판매하는 음식 카테고리가 제외된 모임에서, 어떤 다른 음식이 최종적으로 남았는지 셉니다.** 검토가 끝난 모임만 대상으로 하고, 각 카테고리가 살아남은 모임 수가 많은 상위 5개를 보여줍니다. 여러 음식이 함께 남을 수 있으므로 비율 합계는 100%를 넘을 수 있습니다. 가게 자체가 제외됐다는 뜻과는 구분합니다.

## 13. 통계 화면의 데이터가 실제 이용자의 데이터인가요?

**발표 화면에는 통계가 어떻게 작동하는지 보여주기 위한 시연용 자료를 넣었습니다.** 실제 이용 실적이라고 주장하는 자료는 아닙니다. 집계 기능은 실제 DB에 저장한 주문과 소거 결과를 계산하며, 실제 주문이 쌓이면 같은 방식으로 반영합니다. 시연 자료는 일반 운영 모드의 집계와 분리했습니다.

## 14. 왜 SQLite를 선택했나요? 사용자가 늘어나도 괜찮나요?

**해커톤에서 설치와 관리가 간단하고 데이터를 안정적으로 저장할 수 있기 때문입니다.** 여러 변경을 한 번에 저장하는 트랜잭션도 지원합니다. 현재는 단일 서버와 소규모 사용을 기준으로 만들었고, 여러 서버로 확장하려면 PostgreSQL 같은 공용 DB와 작업·실시간 연결 관리 구조를 함께 정비해야 합니다. 대규모 동시 접속 성능을 검증했다고 말하지 않습니다.

## 15. 제대로 작동하는지 어떻게 확인했나요?

**방장·초대 참가자·사장님을 서로 다른 브라우저 환경으로 나눠 처음부터 주문 수락까지 자동으로 확인했습니다.** 중복 요청, 권한 없는 접근, 가격 변경, 저장 실패, 재접속 같은 경우도 검사했습니다. 카카오 지도는 모의 SDK, 카메라는 테스트 영상으로 확인한 부분이 있으므로 실제 휴대전화와 운영 HTTPS 환경의 현장 검증과 구분합니다.

## 16. 지금 바로 실제 서비스로 운영할 수 있나요?

**핵심 흐름은 동작하지만, 현재는 해커톤 시연 단계입니다.** 실제 운영에는 로그인 공급자 연동, 사업자 확인, HTTPS 배포, 백업과 장애 대응 같은 준비가 더 필요합니다. 현재 소셜 로그인 버튼은 연동 준비 상태이고, 시연 로그인과 운영자 발급 로컬 계정 방식이 구현돼 있습니다. 주문 전달·수락까지 제공하며 앱 내부 결제는 구현하지 않았습니다.

## 발표에서 기억할 짧은 답변

> 카카오맵은 지도와 장소 검색을 맡고, 저희 서버는 조건에 맞는 등록 식당을 찾고 공동 선택과 주문을 관리합니다. 한 사람이 바꾼 내용은 SSE로 다른 참가자에게 전달합니다. QR은 매장을 연결하는 입구이고, 음식 후보는 등록된 정보와 조건으로 거릅니다.
