# 시로 — 앞으로 할 개발 작업

작성일: 2026-10-25 · 기준: [API 기능 목록](시로_API_기능_목록.md), [상세 명세](시로_API_명세서_v1.md), [OpenAPI](openapi.yaml)

## 현재 상태

- **2026-10-25 구현 반영:** 원본 소스 ZIP을 `../dimigo_Hackathon-main/`에 풀고 Express·SQLite API와 프론트를 연결했다. 아래 표는 최초 계획이며, 최신 구현·검증·미완료 운영 항목은 [구현 결과](../dimigo_Hackathon-main/docs/IMPLEMENTATION.md)를 기준으로 확인한다.
- 원본 80개 API의 핸들러, 요청/응답 계약 검증, 서버 권한·상태·멱등성·버전 검사, 공동 소거·식당 선택·QR·주문·사업자 매장/메뉴 관리·수수료 조회·SSE를 구현했다. 브라우저 저장은 현재 로그인 토큰과 개발용 샘플에만 사용하며 실제 파티·주문은 서버 DB에 저장한다.
- 개발 실행은 명시적 시연 로그인과 가상 등록 매장을 사용한다. 운영은 별도 DB와 운영자 발급 계정의 로컬 인증을 선택할 수 있다. SNS 공급자 연동·공개 회원가입·계정 복구·실제 사업자 심사는 미구현이다.
- 지도 클릭·핀 이동과 상세 위치, 선택 약속 시간·무제한 예산, 확인 개수와 검토 완료 동기화, 식당 소거 모션과 실패 복귀, QR의 같은 매장 파티 선택, 주문 옵션·요청 수정, 제출 전 파티 취소, 연결 재시도를 연결했다. 최신 검증 범위는 [구현 결과](../dimigo_Hackathon-main/docs/IMPLEMENTATION.md)를 참조한다. 실제 휴대전화/운영 HTTPS/실제 지도 SDK의 현장 검증과 배포는 아직 하지 않았다.

## 추천 작업 순서

| 순서 | 할 일 | 필요한 구현 |
|---|---|---|
| 1 | 서버·DB와 공통 API 기반 | 서버 실행·배포 환경과 DB 구성. 사용자·식당·메뉴·파티·참가자·후보·소거·주문·수수료 저장 구조 및 프론트 API 호출·오류 처리 연결. |
| 2 | 로그인·게스트·권한 | 로그인·토큰 갱신·로그아웃·내 정보, 초대 게스트 발급. 사용자·방장·사업자의 조회·수정 권한을 서버에서 검증. |
| 3 | 기준 정보와 식당·메뉴 등록 | 음식 카테고리·재료·식사 제한 코드 제공. 사업자 매장 목록/상세/등록/수정, 메뉴 목록/상세/등록/수정/삭제 화면과 API 구현. 가격·옵션·재료·알레르기·품절·숨김·주문 접수 상태 저장. 시연 등록 목록을 실제 DB로 교체. |
| 4 | 파티와 초대 | 파티 생성·상세·조건 수정·취소·내 파티 목록. 초대 링크 생성/복사, 로그인 사용자·게스트 참가, 대기실 참가자 목록·닉네임 수정·탈퇴·강퇴 구현. |
| 5 | 개인 식사 제한 | 개인 제한 조회·추가·전체 교체·삭제 화면과 API, 파티별 최신 제한 확인/취소 구현. 다른 참가자의 개인 제한 정보는 공개하지 않음. |
| 6 | 음식 후보와 공동 소거 | 등록 메뉴·반경·예산·참가자 제한으로 서버에서 후보 생성. 비동기 작업 조회, 후보 목록/상세·열람·소거/본인 소거 취소·진행률·검토 완료/취소·방장 확정 연결. 현재 개인 소거를 파티 공동 상태로 교체. |
| 7 | 식당 후보와 최종 선택 | 확정 음식에 맞는 식당 후보 생성·목록·상세·추가 메뉴 표시. 식당 열람·소거/복구·진행률·검토 완료/취소·방장 확정과 최종 식당 선택 구현. 결과 화면에 실제 선택 식당 표시. |
| 8 | 매장 QR | 사업자의 QR 발급·목록·폐기, 공개 QR 정보 조회, 선택 식당과 파티 연결 구현. 파티 없이 QR로 들어오는 일반 주문 게스트 발급도 지원. |
| 9 | 메뉴 선택·공동 주문 | 주문 생성/복구·파티 주문/주문 상세 조회. 최신 메뉴·가격·옵션을 읽고 본인 메뉴 추가/수정/삭제, 참가자별 선택 완료/취소 구현. 파티 전원 완료 후 방장 제출, 일반 QR 주문은 본인 제출. 제출 후 수정 차단. |
| 10 | 사장님 주문·수수료 | 매장 주문 목록/상세·전체 수락/거절과 사유 표시. 수락 시 수수료 근거 생성, 수수료 목록/상세 조회 화면 구현. 요율 미정이면 계산 대기 처리. |
| 11 | 실시간 공유 | 파티·주문·사업자 매장 이벤트 3종 연결. 참가자 변동, 공동 소거·완료, 주문 변경·제출·수락/거절을 다른 기기에 반영. 연결이 끊겼다가 돌아오면 최신 상태 재조회. |
| 12 | 통합 검증·운영 준비 | 두 기기 이상으로 전체 흐름 검증. 권한 없는 접근·중복 참가/주문 제출·동시 수정·품절/가격 변경·후보 0개·네트워크 실패 처리 확인. 운영 도메인·HTTPS·환경변수·DB 백업·오류 로그 설정. |

실시간 공유는 초대 대기실(4번)부터 붙이기 시작하고, 공동 소거·주문을 구현하면서 이벤트를 늘린다.

## 함께 지켜야 할 규칙

- 파티/주문 단계와 방장 권한은 서버가 판정한다. 소거자의 신원은 공개하지 않고, 다른 사람이 만든 소거는 취소할 수 없다.
- 문서의 `Idempotency-Key`, `If-Match`/버전 검증을 적용해 중복 요청·동시 수정·중복 수수료 생성을 막는다. 후보 생성과 주문 상태 변경은 DB 트랜잭션으로 처리한다.
- 서버가 등록 여부·거리·예산·판매 상태·식사 제한·최종 주문 금액을 검증한다. 후보 생성 시 조건을 저장하고, 주문 제출 시 최신 가격/품절을 다시 확인한다.
- 현재 명세에는 내부 결제가 없다. **식당의 주문 수락은 결제 완료가 아니며**, 수수료 근거를 만드는 기준이다.

## 구현 전에 확정할 부분

- 운영 API 주소·배포 도메인·TLS·영구 SQLite 볼륨·백업 주기·로그인 운영 방식·사업자 소유권 심사, 명세의 임시 운영 정책과 수수료 정책.
- **등록 식당 개수 미리보기 API**는 추가 소비자 계약으로 구현했다: `GET /api/v1/restaurants/nearby-count`. 상세는 [추가 계약](../dimigo_Hackathon-main/docs/api-extensions.yaml)을 참조한다. 사업자 목록 API를 재사용하지 않는다.
- 사용자 화면 반경은 요청대로 200~1000m를 유지한다. 기존 OpenAPI의 넓은 허용 범위와 별개로 이 화면의 제한을 적용한다.

## 우선 완성할 시연 흐름

로그인 → 파티 생성 → 초대 링크로 다른 기기 참가 → 공동 음식 소거 → 식당 소거·선택 → QR 연결 → 각자 메뉴 선택 → 공동 주문 제출 → 사장님 수락.

API 전체 완료 기준: 시연 목록·브라우저 저장에 의존하던 기능이 실제 서버·DB와 연결되고, 위 흐름과 일반 QR 주문을 여러 기기에서 재현할 수 있어야 한다.
