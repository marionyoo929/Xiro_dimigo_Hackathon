# 구현 결과와 운영 전 남은 작업

2026-10-25 · 원본 ZIP을 `dimigo_Hackathon-main/`에 풀어 확장했다. 원본 ZIP과 디자인 이미지는 보존했다.

## 구현한 범위

- 원본 `지침/openapi.yaml`의 80개 작업을 Express API에 연결했다. 요청 본문·쿼리·헤더와 JSON 응답은 복사된 `docs/openapi.yaml`로 검증한다. 프론트 타입도 여기서 생성한다.
- SQLite에 사용자, 해시 처리한 인증 토큰, 매장, 메뉴, 파티, 참가자, 후보 집합, 열람/소거, 생성 작업, 초대, QR, 주문, 수수료, 감사·분석 이벤트를 저장한다. 소규모 단일 서버용으로 리소스별 JSON 행을 사용한다. 주문과 수수료의 유일성은 DB 인덱스로 보장한다.
- 모든 API 명령은 즉시 트랜잭션에서 권한·상태·버전·멱등성을 검사하고 결과와 outbox를 함께 저장한다. SSE 전송은 커밋 후 별도로 수행한다. 제출 가격 충돌은 최신 초안과 완료 해제를 저장한 다음 409로 반환한다.
- 사용자·초대 게스트·QR 주문 게스트·방장·사업자 범위를 구분한다. 다른 참가자의 제한 상세와 소거자, 소거 인원수는 공용 응답 및 이벤트에 포함하지 않는다.
- 로그인·회전·로그아웃, 파티 초대/참가/탈퇴/강퇴/이름 수정, 개인 제한 수정·확인, 비동기 음식/식당 후보 생성, 공동 소거·본인 복구, 전원 완료·방장 확정, 최종 식당 선택을 연결했다.
- 매장/메뉴/재료·제한/가격/옵션/품절/숨김 관리, QR 발급·다운로드·폐기, 파티 연결, 일반 QR 주문, 개인 항목 추가/수정/삭제, 공동 주문 제출, 전체 수락/거절, 수수료 조회를 연결했다.
- SSE 3종은 Bearer fetch 스트림, 본인 전용 열람 이벤트, 24시간 재전송, 커서 만료, 재연결 후 최신 상태 재조회, 연결 종료 시 권한 재검사를 지원한다. 접속 상태는 스트림 연결로 표시하며 오프라인 참가자를 자동 완료하지 않는다.
- 게스트는 종료 또는 24시간 후 만료한다. 게스트 제한은 개인 저장소·파티 전용 제한 스냅샷·인증 주체별 응답 캐시에서 삭제한다. 주문 스냅샷에는 제한을 복사하지 않는다.
- 지도 반경은 200~1000m, 10m 단위다. 새 소비자용 `GET /restaurants/nearby-count`는 DB 등록 식당 수를 계산한다. 원본 계약의 파티 반경 100~5000m는 유지했다.
- 시연 모드에서만 가상 매장과 닉네임/사장님 로그인을 제공한다. 운영 모드는 시연 계정 발급 경로를 설치하지 않는다. 개발 샘플 `/dev/sample-party/menu`도 유지한다.

## 로그인과 데이터

`npm run dev`는 명시적인 시연 모드다. 새 브라우저마다 새 시연 사용자로 시작하며 사장님 버튼은 공통 시연 사업자 계정으로 들어간다. 시연 자료는 `data/demo.sqlite`에 저장된다. 실제 SNS 로그인으로 표시하지 않는다.

운영용 선택지는 `LOCAL_AUTH_ENABLED=true`로 켜는 서버 발급 계정 로그인이다. `npm run create:user`로 사용자/사업자 계정을 만들고, 이메일·비밀번호 검증 → 60초 단일 사용 코드 → 명세의 `/auth/login` 교환을 사용한다. 비밀번호는 scrypt와 무작위 salt로 저장하며 사업자 역할을 클라이언트에서 지정할 수 없다. 기본 운영 DB는 `data/xiro.sqlite`이며 가상 식당·사용자를 자동 등록하지 않는다. 기준 카테고리와 재료 코드는 제공한다.

SNS/OIDC 공급자 검증·콜백·계정 연결과 공개 회원가입·계정 복구는 아직 구현하지 않았다. 로컬 인증은 운영자 발급 계정을 위한 구현이다. 운영 인증 정책에 맞춰 이 부분을 결정해야 한다.

## 검증

- `npm test`: 기존 지도·등록 집계 검증과 8개 API 통합 테스트. 모든 80개 작업의 핸들러 존재, 두 참가자 흐름, 권한/익명성, 후보 0개/전체 소거, 보수적 제한 필터, 게스트 삭제, 옵션/가격 재검증, 멱등성, 동시 수락/거절, 단일 수수료, 토큰 회전, SQLite 재개방, 취소된 작업, SSE 재전송/커서, 실제 로컬 계정 인증을 검증한다.
- `npm run build`: TypeScript 검사와 Vite 배포 빌드.
- `npm run test:e2e`: 설치된 Chrome을 사용한 2개 브라우저 시나리오. 방장/초대 게스트/사장님을 분리한 공동 주문 수락, 새 매장·옵션 메뉴 등록부터 일반 QR 주문 거절까지 검증한다. 카카오 SDK 요청은 테스트에서 차단하고 시연 위치를 사용한다. 320px/390px에서 가로 넘침과 완료 화면도 검사한다.
- E2E는 별도 5174/3002 포트와 임시 SQLite DB를 사용하므로 개발 자료를 수정하지 않는다. 실행 결과와 스크린샷은 `test-results/`에 남고 Git에서는 제외한다.

실제 휴대전화 두 대·운영 HTTPS 환경·실제 카카오 SDK 검색의 현장 검증은 아직 하지 않았다. 외부 지도 테스트는 기존 어댑터 모의 검증과 구분한다.

## 아직 필요한 운영 결정과 작업

1. 운영 도메인·호스팅·TLS 인증서·프록시·영구 DB 볼륨·백업 주기와 복구 책임자 지정. 배포는 수행하지 않았다.
2. 실제 SNS 공급자 또는 로컬 발급 계정 운영 정책, 회원가입/복구, 매장 소유권 확인과 사업자 심사 절차 결정. 이 구현은 소유권 심사를 자동화하지 않는다.
3. 임시 정책 승인: 정원, 기준 코드 목록, 게스트/감사/분석 데이터 및 백업 보관·삭제 정책, 요청률 제한, SSE 보관 기간. 현재 기본 정원 8명, 이벤트/멱등성 보관 24시간이다.
4. 수수료 요율·반올림·과세 정책 결정. 모든 수락 주문은 정책 미정의 `PENDING`, 금액·요율 `null`로 기록한다. 임의의 비율, 청구/출금, 결제 기능은 추가하지 않았다.
5. 부하·장애·복구 검증과 로그 수집/모니터링. 현재는 단일 Node 프로세스와 SQLite용이다. 다중 API 프로세스/다중 인스턴스 배포 전 DB·작업·접속 상태·rate limit을 공유 저장소로 이전해야 한다.
6. 관리자/광고/고급 분석/AI 자유 분류는 이 API 명세의 범위 밖이다. 후보는 등록된 카테고리와 구조화된 재료 코드로 판정하며 외부 AI를 호출하지 않는다.
